# LocateAnything-3B assessment for face recognition

## Executive summary

Do not use or fine-tune LocateAnything-3B to recognize the account owner. LocateAnything is a 3B-parameter vision-language grounding model: it receives an image plus a text/image prompt and outputs bounding boxes or points. It can locate a face, but it is not designed to decide whether two faces belong to the same person.

The current QtmShrimple implementation does not save face bounding boxes or 68 landmark coordinates in MongoDB. It saves one 128-value face descriptor generated by `@vladmandic/face-api`. That is the correct data type for face verification. Accuracy is limited because enrollment uses only one frame, matching uses one descriptor and a fixed `0.6` threshold, and one bad frame immediately locks the UI.

Recommended direction: keep a pretrained face-embedding model, enroll several high-quality samples, compare against a small descriptor gallery, and require temporal consensus. For higher accuracy later, replace face-api recognition with ArcFace/InsightFace while keeping the same gallery-based architecture.

## Scope and methodology

- Conducted: 2026-09-21, Asia/Saigon.
- Local code reviewed: client face enrollment/matching, server schema/controller, calibration UI.
- External sources: NVIDIA Hugging Face model card/license, NVlabs Eagle repository at commit `783f656d127ee498137b5ff52603ce36c292d317`, and the vladmandic face-api tutorial.
- Evaluation criteria: task fit, runtime cost, trainability, deployment compatibility, accuracy, privacy, and license.

## What the current application actually stores

1. Enrollment calls `detectSingleFace(...).withFaceLandmarks().withFaceDescriptor()` in `client/src/components/anti-peep/AntiPeepProvider.jsx`.
2. `detection.descriptor` is converted to an array and sent to `PUT /api/users/anti-peep`.
3. MongoDB stores it as `antiPeepData.faceDescriptor: [Number]` in `server/src/models/User.js`.
4. Runtime detection creates a new descriptor and compares Euclidean distance to the stored descriptor.
5. The 68 landmark positions are passed only to `FaceIDCalibrationModal.jsx` for drawing the wireframe. They are not sent to the server.

The stored 128 numbers are an embedding in feature space, not hand-authored pixel coordinates. The face-api recognition model is explicitly designed to represent a face with a 128-value descriptor and match faces by descriptor distance.

## Why accuracy is currently unstable

| Current behavior | Consequence |
|---|---|
| One enrollment frame | Sensitive to pose, expression, glasses, lighting, blur, and camera quality |
| SSD MobileNet at enrollment, TinyFaceDetector at runtime | Different crops/alignment can shift the descriptor |
| One descriptor per user | No coverage for normal appearance variation |
| Hard-coded distance threshold `0.6` | No calibration against this camera, user, or desired false-accept rate |
| Lock on one mismatch | A single noisy frame causes a false rejection |
| No face returns without action | Anti-peep protection does not react when the owner leaves the camera |
| No liveness check | A photo or replay may pass depending on capture conditions |

## LocateAnything-3B fit

### What it does well

- Open-vocabulary object detection and visual grounding.
- Dense bounding-box/point prediction from natural-language prompts.
- Dataset auto-labeling where the target output is a location.
- Visual-prompt fine-tuning: a crop replaces a category prompt and the model learns to locate matching regions.

### Why it does not solve this feature

- Output is boxes/points, not a stable identity embedding.
- Training data and published benchmarks target localization, GUI grounding, OCR, layout, and pointing—not face verification.
- Visual-prompt fine-tuning still trains localization. The public checkpoint does not support visual-prompt inference without additional fine-tuning.
- Official LoRA script defaults to 8 GPUs, BF16, 16K context, and 5,000 steps. Official full SFT examples use 8 GPUs and 25,000 steps.
- Official training documentation was tested on 8× H100 80 GB. Long-context Magi Attention requires Hopper/Blackwell GPUs.
- Published A100 inference figures show about 11.71 GB peak reserved memory with `la_flash` and 35.12 GB with SDPA for a 4K batch probe. This is unsuitable for a browser webcam loop.
- Model license limits use and derivatives to non-commercial research/evaluation.

LocateAnything may replace a generic face/person detector in an offline annotation pipeline, but that would still need a separate face-recognition model and would be much heavier than the current detector.

## Recommended architecture

### Phase 1: improve the existing browser pipeline

1. Enroll 5–10 descriptors over roughly two seconds: front, slight left/right, neutral expression, normal glasses state.
2. Reject low-quality samples before enrollment: exactly one face, adequate detection score, minimum face size, acceptable yaw/roll, and low blur.
3. Store a descriptor gallery plus metadata:

```js
antiPeepData: {
  isEnabled: Boolean,
  faceDescriptors: [[Number]],
  modelVersion: String,
  threshold: Number,
  pinHash: String
}
```

4. Match a live descriptor against all enrolled descriptors. Use the minimum distance, or `faceapi.FaceMatcher` with multiple descriptors.
5. Tune the threshold with positive samples from the owner and negative samples from other people. Start evaluation near the library's current `0.6` convention, then select the threshold from measured false accepts/false rejects.
6. Require repeated evidence, such as 3 mismatches among the latest 5 valid frames, before locking. Multiple faces may still lock immediately.
7. Add a short no-face grace period, then blur/lock when the owner leaves.

This changes enrollment and matching only. It does not require training a neural network.

### Phase 2: stronger recognition if face-api is insufficient

Use a pretrained ArcFace-compatible embedding model with a modern face detector/alignment pipeline such as SCRFD. Store several normalized 512-value embeddings per user and apply the same gallery plus temporal-consensus logic.

Deployment choices:

- Browser/on-device inference: best privacy and latency; requires ONNX/WebGPU compatibility work.
- Server inference: simpler model runtime and potentially better accuracy; sends face frames off-device and needs explicit privacy, retention, and transport controls.

Fine-tuning a face-recognition backbone should be considered only after collecting a properly consented, multi-person dataset and defining verification metrics. Training on photos of one person alone will mostly overfit and cannot teach the model a useful identity boundary.

## Security findings to fix with the accuracy work

- `antiPeepData.pin` is stored as plaintext and compared in the browser.
- `authMe` returns the full user document, including PIN and face descriptor.
- `getUserById(...).select("-password")` appears to return other users' `antiPeepData`, including PIN and biometric descriptor, because only `password` is excluded.

Hash and verify the PIN server-side. Mark biometric/PIN fields non-selectable by default, return a sanitized user DTO, and encrypt biometric templates at rest. A face descriptor is not a raw photo, but it is still sensitive biometric data.

## Decision

Reject LocateAnything-3B for owner face verification. Improve the existing embedding pipeline first; migrate to ArcFace/InsightFace only if measured acceptance/rejection rates remain inadequate.

## Acceptance metrics for an implementation

- Enrollment produces at least 5 valid descriptors from distinct frames.
- Owner test set covers lighting, glasses, expression, and small head turns.
- Non-owner test set includes several people and printed/screen photos.
- Threshold is selected from recorded distance distributions, not assumed.
- UI does not lock on one transient bad frame.
- PIN and biometric templates are absent from general user API responses.
- No raw camera frames are persisted unless the user explicitly opts in.
